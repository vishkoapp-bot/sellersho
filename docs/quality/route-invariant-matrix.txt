QUAL-01 route invariant matrix | OPEN checkpoint
================================================

Generated registration inventory below is evidence of source wiring, not a
claim of endpoint qualification. Each row identifies a listener and mux
pattern, or a scheduled business job. Prefix patterns may dispatch multiple
actions and methods. "none at registration" does not mean public, unauthenticated,
or safe: the handler may enforce its own boundaries. For the source method,
tenant and object-ownership audit by registration and action, see
docs/quality/route-action-review.md. Runtime qualification and business
invariants remain pending unless explicit evidence is recorded here.

For each action record: method and source, role / capability / tenant / object
boundary, data read or mutated, money or quantity rules, transaction and retry
contract, input limits, and regression evidence. For each job record the same
business invariants with system identity and admission in place of HTTP auth.

Inventory scope: application mux in backend/cmd/server/main.go, separate
metrics mux in backend/internal/observability/metrics.go, and the business
worker registry in backend/internal/worker/operations.go. The process also
runs PollDependencies as telemetry, separately from the business worker.
Search rollup is explicitly unscheduled (worker/scheduler.go).
Per-store host routing and Caddy handling require separate edge review.
The paused backend/internal/networkreward/ package is excluded per task spec.

Check freshness: go run ./scripts/qual-route-inventory.go
Refresh registration rows: go run ./scripts/qual-route-inventory.go -write
The checker and generator read source only, with no HTTP requests or jobs run.

FIRST REVIEW: CUSTOMER WALLET
-----------------------------
Source: backend/cmd/server/main.go and customer_handlers.go, customer wallet
engine migration 202610200002. The mux requires customer capability; handlers
read the principal ID from verified claims and scope queries to customer_id.
The scope is the customer account, not the seller store.

GET /api/v1/customer/wallet | Own balance and locked balance; available =
  balance - locked, clamped to zero; missing row gives zero; SQL errors fail.
  Read only. The guarded wallet regression verifies each of two customers sees
  only their own balance and hold, even with a different customerId in the query.
GET,POST /api/v1/customer/wallet/quote | Own availability; integer Tomans;
  fee 0, net = amount. Read only; eligibility requires an enabled policy and
  amount in the inclusive range from the configured minimum to available
  balance, with amount > 0. Malformed GET amounts return 400 and failed policy
  reads return 500. Reports the configured minimum in minimumAmount.
GET /api/v1/customer/wallet/withdrawals | Own requests and bank metadata;
  read only; SQL rows and iteration errors checked. No cursor is exposed yet.
  Two synthetic customers in the wallet probe saw only their own requests
  even with a customerId query parameter. Defaults to 100 results; accepts
  limits from 1 to 200. Orders by creation time and ID, newest first.
POST /api/v1/customer/wallet/withdrawals | Own request; positive int64 Tomans,
  IR Sheba shape and bounded bank/holder fields. Requires one Idempotency-Key
  (1–128 bytes, trimmed). Atomically adds the hold and inserts a pending
  request with a customer-scoped key digest. No journal until paid. First
  submission returns 201, exact replay returns 200 with the original ID and
  current status, and changed details under that key return 409. Clients
  must keep the same key on retry and use a new key only for a new intent.

FIXED QUAL-01-01: Before the fix, a disabled wallet or below-minimum amount
  could still produce a hold. The writer now reads and locks the settings row
  in the transaction and rejects disabled, below-minimum and unreadable policy
  without a hold or request. The regression checks both quote methods and the
  inclusive minimum, failed reads and invalid amounts.
FIXED QUAL-01-02: Before the fix, identical retries could commit two holds.
  Migration 202611190003 keeps historical identities NULL and enforces unique
  new identities per customer. The wallet row serializes concurrent submissions.
  The regression confirms eight concurrent retries yield one ID and one hold,
  changed payloads conflict, and deliberate new keys and other customers do not
  collide. It also checks that a committed request remains replayable after
  configuration changes and that customer list reads still enforce ownership.
