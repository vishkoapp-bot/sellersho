QUAL-01 route invariant matrix | OPEN checkpoint
================================================

Generated registration inventory below is evidence of source wiring, not a
claim of endpoint qualification. Each row identifies a listener and mux
pattern, or a scheduled business job. Prefix patterns may dispatch multiple
actions and methods. "none at registration" does not mean public, unauthenticated,
or safe: the handler may enforce its own boundaries. All rows remain pending
invariant review unless explicit reviewed evidence is recorded above the marker.

For each action record: method and source, role / capability / tenant / object
boundary, data read or mutated, money or quantity rules, transaction and retry
contract, input limits, and regression evidence. For each job record the same
business invariants with system identity and admission in place of HTTP auth.

Inventory scope: application mux in backend/cmd/server/main.go, separate
metrics mux in backend/internal/observability/metrics.go, and the business
worker registry in backend/internal/worker/operations.go. The process also
runs PollDependencies as telemetry, separately from the business worker.
Search rollup is explicitly unscheduled (worker/scheduler.go).
Per-store host routing and Caddy handling require separate edge review.
The paused backend/internal/networkreward/ package is excluded per task spec.

Check freshness: go run ./scripts/qual-route-inventory.go
Refresh registration rows: go run ./scripts/qual-route-inventory.go -write
The checker and generator read source only, with no HTTP requests or jobs run.

FIRST REVIEW: CUSTOMER WALLET
-----------------------------
Source: backend/cmd/server/main.go and customer_handlers.go, customer wallet
engine migration 202610200002. The mux requires customer capability; handlers
read the principal ID from verified claims and scope queries to customer_id.
The scope is the customer account, not the seller store.

GET /api/v1/customer/wallet | Own balance and locked balance; available =
  balance - locked, clamped to zero; missing row gives zero; SQL errors fail.
  Read only. Cross-customer fixture regression outstanding.
GET,POST /api/v1/customer/wallet/quote | Own availability; integer Tomans;
  fee 0, net = amount. Read only. GET parse errors are treated as zero, and
  a failed policy read is treated as enabled. Boundary tests outstanding.
GET /api/v1/customer/wallet/withdrawals | Own requests and bank metadata;
  read only; SQL rows and iteration errors checked; currently unpaginated.
  Cross-customer fixture and bounded-read review outstanding.
POST /api/v1/customer/wallet/withdrawals | Own request; positive int64 Tomans
  and IR Sheba shape; atomically adds amount to the hold with a balance guard
  and inserts a pending request, no journal until paid. Fresh UUID on each
  successful submit; no stable retry identity. See open findings below.

OPEN QUAL-01-01: Wallet withdrawal admission disagrees with configuration.
  Source-level case: a synthetic customer has balance=10000, locked=0 and
  wallet_withdraw_enabled=false. A valid quote for 5000 reports disabled;
  the POST writer does not consult that flag. The migration also defines a
  minimum that neither handler reads. Add a guarded, migrated DB regression:
  verify denied submissions leave both the hold and requests unchanged, verify
  allowed minimum boundary, and fail closed when policy is unavailable. Do
  not qualify the path until the regression runs and enforcement is verified.
OPEN QUAL-01-02: Wallet withdrawal retry identity is missing. Source-level
  case: balance=10000, locked=0, identical synthetic 4000-Toman submit twice.
  Current write path can create two pending requests and lock 8000; define
  a stable client intent ID without deduplicating deliberate same-amount
  requests. Add guarded concurrent/retry conservation and ownership tests.

BUSINESS JOBS: EXISTING JOB-01 CONTRACT AND EVIDENCE
---------------------------------------------------
The system worker has no HTTP tenant principal. Short, owner-checked database
leases and nonqueued process slots gate admission. Candidate predicates scope
each write. See docs/operations/background-jobs.md for retry, deadline, crash
recovery and local regression commands. Application endpoint authorization,
including the administrator's delivery run-now action, is a separate review.

unpaid-order-expiry | Up to 200 overdue unpaid orders; guarded per-order
  cancellation; release existing Redis holds idempotently by order ID. No
  inferred inventory or captured-money cancellation. Evidence: JOB-01 burst,
  crash/restart and payment deadline regressions.
ad-cleanup | Remove only expired ad data, max 2,000 rows per table. Bounded
  SQL selection skips locked rows; deleted rows no longer match retries. No
  ad balance or inventory formula. Evidence: JOB-01 bounded-job regressions.
qc-response-deadline | Up to 100 overdue QC cases, bounded SQL selection
  skips locked rows. Escalates case state rather than moving physical stock.
  Evidence: JOB-01 bounded-job regressions and operations integration tests.
supplier-sla | Up to 100 suppliers; recompute dispatch eligibility on the
  90-day sample with strict >98% and approved/active and admin-grant guards.
  Candidate transactions under advisory lock. No money write. Evidence:
  JOB-01 bounded-job and supplier poison-candidate regressions.
delivery-lock-releaser | Up to 100 orders per stage. Auto-confirm after 20
  days; release only after configured return window and guarded recheck.
  Per-candidate transactions keep profit/referral and ledger in sync; retries
  re-read eligibility. Evidence: JOB-01 guarded balance and crash regressions.
monthly-settlement | Max 25 accounts per batch. Scheduled and manual paths
  share durable month/account progress and transaction guards. Use canonical
  account availability and do not add cumulative figures again on retry.
  Evidence: docs/architecture/monthly-settlement.md and JOB-01 restart tests.
