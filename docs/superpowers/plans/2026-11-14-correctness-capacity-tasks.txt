CAPACITY AND BUSINESS ACCEPTANCE CONTRACT
=======================================
Correctness, 1,000 users, and 100 RPS deployment acceptance

Status: proposed engineering acceptance criteria and task backlog, 13 November 2026. No implementation, capacity
  certification, or production release is implied by this document.

Goal and baseline

Make Sellersho's stock, order, payment, and accounting flows reconcile under retries and concurrent requests,
  then demonstrate 1,000 concurrent signed-in user sessions and sustained 100 total API requests per second on
  the intended deployment hardware. The user requested 1,000 starting users; this plan conservatively interprets
  that as concurrent active sessions. Keep the existing Go monolith, PostgreSQL, Redis, React, Nginx, and Caddy
  architecture unless measurements show a specific change is necessary.

The audited revision is 07aff40ffc8914a9deaa153aa7894b9d3fd73400. The audit produced 14 failing database
  invariant reproductions and four groups of frontend reproductions. Ten existing SKU inventory integration
  tests passed. The isolated existing Go baseline had 157 top-level passes, five failures, and 222 skips; the
  frontend had 208 passes and two failures. The frontend production build passed. These results reject a
  correctness sign-off; they do not measure production capacity. Detailed local evidence is in
  ../../../../audit-artifacts/ relative to this file's directory, outside the repository; task acceptance
  criteria must remain usable without that directory.

Global constraints

- Capacity means 100 total externally received API requests per second, not 100 completed checkouts per second;
  revise the workload if the business target differs.
- Starting user capacity means 1,000 concurrent active signed-in sessions with isolated identities, carts, and
  orders; it does not mean 1,000 simultaneous database connections or 1,000 checkouts per second.
- Keep PostgreSQL authoritative for stock and money; Redis and browser caches cannot authorize a stock capture,
  refund, debit, or payout.
- Use the established integer monetary unit, checked arithmetic, and an explicitly documented rounding rule at
  every conversion; never silently change a pricing formula to satisfy a stale test.
- Every stock or money mutation must preserve its business invariant in one database transaction and be safe to
  retry after an ambiguous response.
- Historical corrections require attributable evidence and an auditable correction; ambiguous history must enter
  reconciliation, never an invented balance or silent rewrite.
- Test and benchmark only explicitly disposable environments; never infer a test database from localhost, a
  development label, or production credentials.
- Preserve existing services and primary-site access; exclude docs/fa/ and paused
  backend/internal/networkreward/ from changes and releases.
- Follow AGENTS.md for authorized implementation and release: validate, commit, push, then use deploy.ps1;
  protect secrets and rehearse database compatibility before production.

Business invariants

1. A physical unit has one lifecycle position. Supplier sellable, warehouse sellable, reserved, in transit,
  staging, quarantined, damaged, dispatched, and returned movements cannot create the same unit twice. Model
  current on-hand states separately from cumulative departures; do not sum overlapping projections. Receipt and
  approved adjustment are attributable external sources; shipment, disposal, and supplier return are
  attributable departures.
2. Capture follows the persisted SKU, location, and fulfillment-origin split. A routed warehouse line cannot
  silently consume a supplier lot. Cancellation restores only the exact eligible allocations; dispatched goods
  become sellable again only after a recorded acceptable return receipt.
3. Bin capacity follows actual placement and physical departure, using SKU dimensions/weight. A sale reservation
  and a physical shipment are distinct events.
4. One authoritative signed financial balance feeds display, statements, payout, service purchase, monthly
  settlement, refunds, and fees. All competing writers take compatible locks before making a debit/reservation
  decision. Debt remains visible.
5. A business event has one effect even with different client retry keys, duplicate callbacks, worker restarts,
  or out-of-order delivery. A paid cancellation records the refund obligation even when the external provider is
  unavailable.
6. Receipt age and quantity history determine storage fees. New units cannot inherit past occupied days;
  departure cannot erase accrued charges. Ledger postings and their reversals reconcile to statement closing
  balances and treasury liabilities.
7. The server validates price, discount, delivery quote, quantity, ownership, and authorization. Browser state
  is scoped to authenticated identity and store; stale async responses cannot restore a logged-out session or
  replace a newer quote.

Capacity contract

These are initial acceptance targets, not observed results. The release evidence must identify CPU model/count,
  RAM, disk class, OS, exact application/image versions, PostgreSQL/Redis settings, number of replicas, pool
  sizes, and other services sharing the host. Measure generator CPU and network too. A test on a developer
  machine does not certify a different production host.

Provision 1,000 distinct authenticated users and maintain their independent session/token/cookie state
  throughout the qualifying run, distributed across stores and roles according to the intended audience.
  Exercise all identities, rather than reusing one token 1,000 times. Run both (a) the fixed 100 RPS
  arrival-rate workload and (b) a closed-loop 1,000-user journey simulation with realistic think time, reporting
  its actual throughput. At 100 RPS, 1,000 active users average one API request per user per ten seconds; page
  fan-out and checkout bursts must be counted explicitly. The closed-loop run alone cannot certify 100 RPS
  because slow responses can lower its offered load.

Run a separate startup login ramp of 1,000 distinct users over 60 seconds, and repeat it with background
  browsing so total offered API traffic reaches 100 RPS. Count each authentication flow's real requests,
  including any challenge/verification calls; use a synthetic adapter instead of sending real SMS at load-test
  rates. Test expiry/refresh/re-login at configured lifetimes and concurrent device sessions. Assert no
  cross-user or cross-store data leakage, cart/key reuse, involuntary global logout, or unbounded retained
  session state. Use a small real-browser cohort for UI behavior and protocol-level clients for the
  1,000-session capacity run; 1,000 local browser processes are not required.

Use a separate load generator and the public TLS path through Caddy/Nginx. Count external API requests
  separately from Caddy domain-authorization subrequests, provider calls, probes, and assets. Also run a
  browser/static-asset burst to measure their additional domain-authorization load. Match the production worker

Required contention and failure scenarios

- One hundred simultaneous order captures compete for the last five valid units: exactly five inventory captures
  and five allocations. Reject excess attempts before external payment capture where the provider flow permits
  it. If money was already captured externally, preserve the paid fact and create one durable
  refund/compensation obligation; never fabricate available stock or erase the confirmed payment.
- One hundred deliveries of one callback, including different transport retry keys: one financial effect and one
  inventory capture.
- Concurrent cancellation/dispatch, receipt/capture, refund/payout, and automatic/manual settlement:
  conservation and balance invariants hold; retries and deadlocks are bounded.
- Crash after provider verification, after transaction commit before response, and during worker execution:
  restart/reconciliation converges to one recorded outcome.
- Redis restart/loss, database connection loss, and provider timeout: readiness reflects dependencies, mutations
  fail safely, obligations survive, and recovery is measured.
- Account A to B switch with delayed A responses, stale shipping quotes, maximum/invalid quantities, rounding
  boundaries, partial return after split fulfillment, and legacy/V2 mixed inventory: deterministic tested
  outcomes.

Release evidence and operations

All confirmed audit bugs require regression tests and remediation before enabling affected commerce paths.
  Investigation tasks close with evidence of either a fix or a verified non-defect; merely relabeling a risk
  does not close it. The real payment adapter is a launch blocker for a store accepting actual payments.
  Provider selection and credentials are external inputs, not reasons to replace verification with a mock.

Migration rehearsals must cover an empty database and a representative previous production schema/data snapshot
  in a disposable environment. One serialized tracked runner must fail on errors. Expand/contract changes must
  remain compatible with the rollback application; restoring a backup is disaster recovery, not a routine
  rollback that discards new orders.

Before launch, restore a backup into a fresh isolated environment and verify order, stock, ledger, upload,
  configuration, and payment-obligation integrity. Initial operational objectives are RPO <= 15 minutes and RTO
  <= 60 minutes, subject to infrastructure feasibility and business confirmation; implement WAL/PITR or an
  equivalent mechanism and prove the targets if adopted. Assign a named incident owner, alerts, on-call contact,
  reconciliation schedule, and capacity rerun policy. A successful archive listing is not a restore drill.

The go/no-go record must link the commit/image digests, migration results, complete test reports (including skip
  reasons), raw load-test output, dashboards, restore drill, rollback rehearsal, historical reconciliation,
  unresolved-risk decisions, and payment sandbox evidence. No plan checkbox can substitute for those results.

SHARED INVENTORY INTERFACES
===========================

* No silent replenishment: receipt cannot infer new stock from an exhausted/missing source balance. New
  shipments use sourceKind='transfer' unless an explicit 'external_replenishment' line records a unique external
  receipt reference and reason. A transfer reserves its exact supplier lot when booked, moves it to transit on
  explicit dispatch, then consumes its allocated transit quantity on receipt. Cancellation releases only
  undispatched reservations. External receipts credit once, after authorized warehouse verification, and cannot
  also debit/reuse a transfer allocation. Existing unknown shipments require reconciliation; they are not
  automatically reclassified as new goods.
* Keep one source debit: the transfer task owns the debit. QC and putaway only change state/location of those
  same allocated units. Do not retain the old QC supplier debit after adding the upstream debit. Every receipt,
  correction, disposition, cancellation and departure has database-enforced business identity independent of
  client retry keys.
* Common origin type proposed in backend/internal/repository/inventory_origin.go: InventoryOrigin { Type string;
  SupplierID, WarehouseID, SupplierWarehouseID string }. Allowed Type: supplier, warehouse, legacy. Legacy means
  explicitly unattributed history, never a wildcard for a named origin. InventoryAllocation { BalanceID string;
  Quantity int; Origin InventoryOrigin } extends existing allocation JSON compatibly; original balance IDs
  remain immutable.
* Transfer interface proposed in backend/internal/repository/inbound_inventory.go: reserveInboundTransferTx(ctx
  context.Context, tx *sql.Tx, shipmentID, supplierID, warehouseID string, lines []InboundTransferLine) error;
  dispatchInboundTransferTx(ctx context.Context, tx *sql.Tx, shipmentID string) error; receiveInboundLineTx(ctx
  context.Context, tx *sql.Tx, lineID string, cumulativeReceived int, actor string) error. InboundTransferLine
  contains ProductID, VariantID, SourceKind, ExternalReference, Reason strings; Quantity int; Source
  InventoryOrigin. Quantity and IDs are validated before writes. SKU can be empty only for legacy unallocated
  stock.
* Preserve captureOrderInventoryTx/restoreOrderInventoryTx outer signatures. INV-05 replaces allocation
  internals with consumeInventoryForOriginTx(ctx context.Context, tx *sql.Tx, item inventoryCaptureItem, mode
  string, origin InventoryOrigin, quantity int) ([]InventoryAllocation, error). It consumes all persisted
  order-origin splits; it does not pick the first split or change origin after payment.
* CORE-01 owns the one global lock order, including payment, account and storage rows; all inventory helpers and
  callers must adopt it. External carrier/PSP calls remain outside stock transactions with durable replay state.
* Migration/reconciliation rule: new metadata is additive first. Backfill only from unique immutable links such
  as inbound destination, exact capture balance IDs, task-to-bin records and existing movement IDs. Do not
  allocate NULL variant history across SKUs, infer supplier warehouse from the product's current origin,
  decrement anonymous stock to 'repair' it, manufacture historic receipts, or bill fabricated historical
  storage. Unresolved stock is excluded from named-origin promises and surfaced for counted reconciliation with
  audit evidence. Keep existing paid orders operationally visible as exceptions; do not silently cancel them or
  let a read hide them.


SHARED FINANCIAL INTERFACES
===========================
Use one transaction-aware financial service over existing domain tables. This
does not require an unrelated event-sourcing rewrite. Proposed interfaces/names:
  LockAccountsTx(ctx, tx, orderedAccountKeys)
  BalanceTx(ctx, tx, accountKey, currency) -> BalanceSnapshot
  ReserveDebitTx(ctx, tx, accountKey, amount, businessKey, requestKey) -> Reservation
  PostMoneyEffectTx(ctx, tx, effect, businessKey) -> ExistingOrCreatedEffect
  ReadBalances(ctx, accountKeys, currency, asOf) -> coherent report snapshot
Account keys distinguish seller, supplier and customer, not an untyped ID string.
BalanceSnapshot exposes signed posted balance, outstanding reservations, signed
available = posted - reserved, debt, currency/unit, and snapshot/version metadata.
The UI may display max(0, signedAvailable) as spendable, but debt must remain
visible to accounting; GREATEST(0) must not erase liabilities in treasury totals.

1. All paths that change a balance/reservation acquire the same affected-account
   locks: payout, early withdrawal, service purchase, refund reversal, adjustment,
   release, withdrawal approval/rejection, transfer completion and settlement.
   Multiple accounts lock in deterministic account-key order. Coordinate the
   cross-domain order/payment/return/inventory lock order with the order workstream
   before implementation; do not introduce a competing order in finance code.
2. Authorization computes BalanceTx in the same transaction after the locks,
   without cached reports or a separate *sql.DB read. Either one canonical SQL
   statement or an explicitly coherent transaction snapshot computes all terms.
3. Balance terms include released profit/commission/bonus, signed adjustments,
   return reversals, finalized outgoing payments/purchases/fees, and outstanding
   reservations. Define each status exactly once. An approved early withdrawal
   has a net payout plus its fee; gross and linked net must never both reserve.
4. ReserveDebit rejects nonpositive amount, currency mismatch, insufficient signed
   funds, overflow or failed reads. A legitimate later refund may create debt;
   do not suppress a customer's refund because a seller already withdrew. Freeze
   further spend and surface recovery liability instead of clamping it away.
5. Business uniqueness uses the domain event identity (parcel charge, order refund,
