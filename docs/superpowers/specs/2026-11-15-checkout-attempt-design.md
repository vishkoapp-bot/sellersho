# CHECKOUT-01: durable logical checkout

The approved backlog requires a logical checkout to survive response loss, reload, double clicks and concurrent tabs without creating a second order. This follows the standing instruction to implement and release each stage; implementation choices below are the implementer's calls.

## Approach and boundaries

A disabled button alone loses its identity on reload. A permanent cart-derived key prevents deliberate repeat purchases. Use an opaque random attempt ID, a normalized immutable request fingerprint, durable account-scoped browser coordination and server-side atomic order linkage instead. Keep the current React/Go/PostgreSQL stack and add no dependencies. Saved address and shipping quote resolution still happen for a new order, but an existing committed order is recovered without repricing or reloading a deleted address.

Browser IndexedDB stores only immutable account/store scope, attempt ID, request hash, acknowledged order ID, never contact/address data, credentials or monetary snapshots. An atomic read/write transaction selects one active attempt per immutable account (across tabs). Each request still carries its normalized payload from the form. If its hash differs from the unresolved attempt, block creation and offer recovery or explicit abandonment. Completed attempts remain replayable until the user explicitly starts a new purchase. This allows two deliberate identical purchases while stale in-flight requests retain their original identity. Unsupported/unavailable durable storage fails closed rather than silently rotating an uncertain key.

Server migration 202611150005 adds checkout_attempts keyed by authenticated customer and attempt ID, immutable fingerprint, open/completed/abandoned state and unique order link. Register an attempt before expensive validation. Matching repeats can continue; changed payload gets 409. Order insertion, new immutable order-item product_title_snapshot values and attempt completion share one SQL transaction, locking the attempt row first. Historical NULL titles explicitly retain the existing catalog fallback; no historical descriptions are invented. Item query, scan and iteration errors propagate rather than returning partial successful recovery. Concurrent request losers return the winner's stored order and skip notifications/address/code-use effects. No lock/transaction spans external provider I/O. Legacy orders and unkeyed compatibility callers remain intact; unknown-fingerprint historical keys cannot be silently bound to a new request.

Authenticated GET /api/v1/checkout-attempts/{id} recovers only that customer's order and state. POST to the same path with an explicit abandon action locks the same row; when absent it inserts an abandoned tombstone, so a delayed original request cannot create an order afterward. Abandonment never cancels or refunds an already-created order: it returns the completed outcome instead. No automatic restart after 404/network error. Acknowledging a resolved/abandoned attempt and requesting a new purchase rotates the browser pointer conditionally; late old-tab completion cannot replace it.

OrderProvider exposes recovery and explicit new-purchase actions and retains session-generation checks around every asynchronous result and durable mutation. CartDrawer shows a compact recovery notice with recover and explicit new-purchase controls. Recovering an existing order uses its stored lines, never a changed cart's lines. An existing/recovered order does not automatically start another payment intent. Payment creation retains existing server guards. A new order remains visibly pending if its token request fails. Wallet checkout remains disabled.

## Acceptance and review focus

Mounted OrderProvider browser regressions: committed response lost then retry; double submit; reload; simultaneous same-origin tabs; logout/new identity and stale responses; changed payload blocked; explicit abandonment racing delayed create; two deliberate identical purchases. Storage failure must send no mutation. Backend integration tests assert one actual order and item set, no duplicate supplier allocation, payment intent/stock/ledger unchanged by replay, ownership 404, same-key changed-payload 409, replay after saved-address deletion or quote changes, atomic completed-versus-abandoned race, and legacy-key handling. Exact committed snapshots are returned, not current catalog values.

Migrations 001-004 remain immutable. Use disposable migrated PostgreSQL/Redis for all mutation tests. Exclude docs/fa and paused networkreward from release. Run relevant red/green tests, complete frontend/typecheck/build and isolated Go regression gates, independent code review, commit, push, deploy.ps1 -BuildOnServer and verify release marker, health, migration checksums and unchanged production financial totals. Production-equivalent 1000-user/100-RPS certification remains open.
