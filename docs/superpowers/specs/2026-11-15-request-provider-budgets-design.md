# OPS-02: bounded request and provider outcomes

Implement the approved OPS-02 backlog after CHECKOUT-01 production85f655a. Keep Go/React/PostgreSQL/Redis/Caddy/nginx and existing context-aware SQL; no dependencies or new background handler goroutines. The implementer chooses the concrete budgets below under the standing instruction to execute and release without repeated approval.

## Approach

Transport timeouts alone leave business SQL/provider work alive. Blanket retries can duplicate SMS, shipment registration or payment. Use explicit route context deadlines, socket read/write deadlines, nonblocking admission, and shared provider budgets with an allowlist of read-only retries. Keep ambiguous mutations durable and recoverable through existing order attempts, finance operation IDs and Tapin attempted markers. A fresh read-only builder review checks this design before inline implementation.

## Budgets and admission

Normal API:8s route context,10s socket write, nginx13s read, Caddy14s response-header wait, browser15s. Internal domain authorization2s, Caddy forward-auth4s. Image upload (POST product-image or exact supplier product/variant image collection):60s route/read,65s socket write, nginx68s, Caddy70s, browser75s. Static downloads20s write and bounded upload10MiB remains existing. Ordinary synchronous exports retain8s and bounded existing result limits; bigger exports require a durable job rather than a hidden timeout increase. Global server read header5s, read65s, write70s, idle60s; route socket deadlines enforce the shorter class on the nginx HTTP/1 upstream. Standard ResponseController Unwrap support preserves instrumentation. Unsupported test writers fall back to context; live HTTP tests prove socket behavior.

At most64 ordinary API handlers and4 image uploads per process; overload returns503 with retry-after1 and no waiting goroutine. Deadline middleware runs handlers synchronously, propagates cancellation, never buffers full responses or detaches work. A deadline before headers yields504 JSON: reads may retry, mutations explicitly have unknown outcome. An already-started response is truncated/closed, never rewritten as a false success. No automatic browser mutation retries. Caller cancellation is composed with the browser's own timeout rather than disabling it.

Provider executor is shared per provider across client instances: Tapin16 concurrent/32 requests per second/burst32; IPPanel8 concurrent/8 per second/burst8. Nonblocking semaphore plus bounded token bucket, no pending queue. Provider logical call5s, safe read attempts2s each, at most2 attempts with bounded exponential jitter100-250ms; unsafe mutation uses one5s attempt. Earlier enclosing deadlines win; cancellation interrupts backoff/body reads and releases capacity. Response bodies bounded at existing caps1MiB Tapin JSON/8MiB label/4KiB SMS. No URLs, payloads, phone numbers, tokens or response bodies enter executor telemetry/errors. Fixed provider/operation/outcome labels expose overload/timeouts; no dynamic label values.

Retry only transport failures,408/429/5xx for explicitly safe operations. Tapin options/check-price/filter POSTs and label GET are reads; registration is never retried. IPPanel credit/recipient GETs may retry; sending SMS is never retried. Authoritative business rejections are not retried. Locally rejected provider admission reports503; a new Tapin attempted marker can be cleared only on proven pre-send rejection, never on timeout/unknown. Verified captures and existing payment/refund keys remain unchanged; actual PSP integration belongs to FIN-010 and receives the same bounded-call contract when connected.

Redis also has an explicit bound: the current go-redis defaults ignore context deadlines for socket I/O and retry commands. Configure ContextTimeoutEnabled=true, no automatic retries, dial1s/read2s/write2s/pool wait1s and at most32 active connections. Parent deadlines shorten these limits. Apply the same production option configuration in guarded test Redis fixtures. A real loopback proxy to the marker-verified disposable Redis stalls reservation replies: the command must time out within its context, issue no duplicate mutation and never send SMS without a confirmed reservation. This addresses the builder review's sole important question.

## OTP uncertainty

Existing per-phone30s resend cooldown,120s code lifetime and five-attempt verification guard remain the abuse controls. Reserve cooldown and code atomically in Redis BEFORE sending SMS, reset the new code's verification counter atomically, never expose it in a response. Missing Redis fails closed before send. A successful send retains the reserved code. Unknown transport/5xx/truncated success keeps both code and cooldown so a delivered code is usable and a response-loss retry cannot send again. A proven rejection/pre-send overload may conditionally clear only that generation's code/cooldown, never a newer request. Cancellation must not trigger an unbounded cleanup transaction. Existing production/dev behavior is preserved except false successful unrecorded OTP is rejected. No real messages or PSP operations in tests.
