# FIN-007: Coupon reservations attached to orders

Status: design for the authorized FIN-007 implementation, after FIN-005. Source requirement: `docs/superpowers/plans/2026-11-14-correctness-capacity-tasks.txt:1410-1438`. This is one coupled release, not separately deployable schema, checkout and payment changes.

## Policy and invariants

Reserve one coupon use when its discounted order commits; consume it when payment confirmation is durably recorded; release it once on eligible unpaid cancellation/expiry. Consumption is permanent, including subsequent refunds, returns and paid cancellations. A released reservation never becomes reserved or consumed again. Verified money arriving after release preserves its receipt and enters FIN-003 cancellation/compensation; it never resurrects fulfillment or competes for another coupon slot.

`used_count` becomes occupied capacity: reserved + consumed + review-held reservations. Unlimited means `max_uses IS NULL`; it still records reservations/counts. New admission requires active, `starts_at <= database clock < ends_at`, unchanged priced coupon identity/version, and available capacity. Existing accepted orders keep their amount and reservation after coupon expiry/deactivation. Date/term changes affect new admission only. Zero actual coupon benefit creates no new reservation and stores no code; campaign/widget/sale discounts alone never use coupon capacity.

The order, its lines/origins/shipments, coupon reservation, count and checkout-attempt completion commit or roll back together. Same authenticated customer/key/fingerprint returns the original order before checking current coupon availability or pricing. Different payload conflicts. Exhaustion is an explicit pre-commit `409 coupon_exhausted`, never a silently full-priced order. Invalid or changed terms are `409 coupon_invalid` / `409 coupon_changed`; the existing advisory invalid-code check can retain its current 400 response.

Global constraints:

- Add `202611170001` only; never edit applied migrations.
- Preserve persisted prices, FIN-001/003/005/012 money facts, source evidence, refund liabilities and transaction ordering. No real provider calls.
- Exclude `docs/fa/` and `backend/internal/networkreward/` from reads, tests, compilation, commits, frozen validation archives and deployment.
- Validate only in a frozen source archive excluding protected paths, using guarded disposable PostgreSQL; never root `go test ./...` in the working checkout.
- Root owns final review, full gate, commit, push and `deploy.ps1 -BuildOnServer`; preserve server credentials, services and primary-site access.

## Evidence and additive schema

Add coupon `revision BIGINT NOT NULL DEFAULT 1`; increment on actual mode/value/window/active/max-use changes. Existing coupon identity `(id,store_id,code)` becomes immutable once referenced. Reject deletion of referenced coupon/store/order, including cascades; deleting unused codes remains permitted. Reservation evidence must survive account cleanup. Do not silently rebind an old code to a replacement row.

Add nullable `orders.coupon_discount_amount BIGINT`: exact coupon-only Toman amount for new discounted orders; null for historical attribution that cannot be proven. Add corresponding `pricing.DiscountResult.CodeDiscountAmount`, preserved through campaign aggregation, widget and variant-sale layering. The existing `seller_discount_amount` contains all these layers and is **not** coupon-only. New amount is bounded nonnegative money, positive when a new reservation is attached, and no greater than the persisted seller aggregate. Carry trusted expected ID/revision as non-JSON admission fields in `domain.Order`; client JSON is not evidence.

Create `order_coupon_reservations`, primary key `order_id`, with `coupon_id`, `store_id`, normalized code, exact accepted `seller_discount_amount`, nullable coupon-only amount, nullable accepted coupon revision, `state` in `reserved/consumed/released/review_hold`, `evidence_kind` in `admission/legacy_snapshot`, timestamps and reason. Foreign keys bind real order/coupon; deferred consistency checks bind store/code/amount to the order snapshot. Identity and money evidence are immutable; transitions are only reserved -> consumed/released/review_hold and review_hold -> consumed/released after proven evidence/review. Terminal consumed/released cannot change. Append `order_coupon_events` with unique `(order_id,event_kind)` transition identities and prior/new state, reason/time; no duplicate use on replay.

Create `coupon_reconciliation_issues` for immutable migration observations: order/coupon references when known, normalized store/code identity, old count, rebuilt count, reason and source snapshot. Record missing/ambiguous identity, invalid/contradictory amounts/statuses, unresolved payment evidence and historical oversubscription. Unresolved identity issues block new admission for that normalized store/code, including recreation. A simple query/report is sufficient; no new UI or broad reconciliation service. Explicit reviewed resolution must retain the original issue and evidence; automatic guessing is forbidden.

`used_count` equals the number of occupied ledger rows for that coupon. Update it only while holding the coupon guard and only with the matching reservation transition; consume does not change count, release decrements once. Deferred consistency verifies touched coupon totals. Do not add `used_count <= max_uses`: legitimate reconciliation can reveal historical oversubscription. New reserve alone checks capacity. Use checked count arithmetic and fail migration on integer overflow rather than wrapping.

## Transaction protocol

Add `seller_discount_codes` rank **350**, between typed principals (300-302) and products (400). Reservation/events are subordinate to the owning order and coupon, not independently acquired late locks. Extend `lockOrderFinanceTx` to discover and prehold the coupon before products using its existing `TransactionLockSet`; its existing-order `FOR UPDATE` prefix remains unchanged. Do not call a new coupon-lock helper after `lockOrderFinanceTx`, which already holds products. Empty order code avoids reservation-table queries in narrow historical fixtures; fixtures still need `discount_code` and shared INSERT/reader `coupon_discount_amount` columns. Nonempty code with missing schema/unexplained evidence fails closed in production. A matching immutable migration-origin missing/ambiguous-identity issue is the narrow financial-fact exception described below.

Checkout-attempt guard is a creation-only prefix: no existing-order lifecycle operation subsequently acquires an attempt. Creation uses an explicit compatible-parent protocol because it performs no balance authorization. Discover the **complete** existing principal/FK-parent set for the order and every planned item/origin/shipment before inserting anything. Prehold all referenced stores (order store and referrer), suppliers (origins and supplier shipments) and customer users with `FOR KEY SHARE`, in canonical rank/table/bytewise-ID order: stores 300, suppliers 301, users 302. Never upgrade these guards during creation or call the existing `FOR UPDATE` financial prefix from creation. Two creators in one store can therefore coexist, while an existing lifecycle `FOR UPDATE` guard still conflicts in the same acquisition order.

Only after this complete principal prefix, INSERT the new private order. This unpublished-row INSERT is the explicit exception to acquiring existing orders at rank 100. A primary-key collision aborts the transaction or uses established checkout replay in a fresh transaction; never proceed as if a colliding existing row were private. Parent-before-INSERT ordering prevents implicit customer/store FK acquisition inversion; inserting first and merely avoiding later upgrades is insufficient.

Then acquire the coupon `FOR UPDATE` at rank 350, prehold all referenced products 400 and variants 500 with `FOR KEY SHARE`, followed by remaining origin FK parents warehouses 550 and supplier_warehouses 551, each in bytewise-ID order, before subordinate INSERTs. These two parent relations get explicit creation-contract ordering and catalog coverage. The full FK inventory must be checked against the migrated real schema: `orders` references customer/store/referrer; `order_items` references products/variants; `order_item_origins` references suppliers/warehouses/supplier_warehouses plus the new private order/items; `supplier_shipments` references suppliers plus the private order. `shipping_quote_id` is text, not an FK. Private new subordinate rows need no competing existing-row guard. Revalidate discovered identity/ownership through the same tx; discovering an omitted earlier parent aborts and restarts, never acquires it late. Do not upgrade any creation `KEY SHARE` guard. Future balance/stock authorization would require a separately designed complete guard plan, not an opportunistic upgrade.

Bind coupon ID/store/normalized code/revision and exact server-priced amount after its lock; evaluate current database clock after lock wait, not transaction-start `NOW()` for admission. A mutation between pricing and admission returns changed/invalid, without repricing an accepted order. Replay an existing reservation only if every immutable payload field matches. The new compatibility restrictions classify coupon backing under the locked order identity; they must not change `SetPaymentStatus` or `UpdateOrderFulfillment` semantics for unrelated nondiscounted orders.

All helpers use caller `context.Context` and `*sql.Tx`; no nested tx, `*sql.DB` authorization, network/Redis/provider calls while holding rows, pooled/global marker, or new global mutex. Standalone coupon metadata changes lock only the coupon and never subsequently acquire orders/principals. Use bounded whole-transaction retry for PostgreSQL retryable errors; programming/identity errors are not retries. Independent coupons/stores must remain independent.

## Eligibility and late money

Eligible release means canonical cancellation/expiry committed, no inventory/fulfillment admission, no consumed state, no independently confirmed receipt, no paid/refunded historical marker and no unresolved verification inquiry or ambiguous payment evidence. Merely `payment_status='failed'` proves none of these. Unknown inquiry or inconsistent historical money retains capacity as review_hold; a later valid receipt consumes that held slot even if the cancelled order receives a refund. No automatic expiry of review holds.

If release wins before an inquiry/receipt is admitted, later money uses the existing durable receipt and FIN-003 obligations; reservation remains released and another order's use remains intact. The verification transaction must ensure cancelled status/compensation without attempting inventory. If confirmed receipt wins first, coupon becomes consumed; later cancellation retains consumption and creates the normal refund obligation. A crash after receipt but before stock admission must leave one consumed use and recoverable payment/compensation, never a free coupon or second receipt.

Legacy `MarkPaymentPaid` without a structured receipt cannot certify gateway cash. It may retain existing compatibility fulfillment semantics for held, valid historical orders, but converts reserved to review_hold; it must never admit a released discounted order. Simulated receipts retain their funding kind and existing no-real-money execution restrictions.

A retained migration-origin `missing_identity`/`ambiguous_identity` issue matching the locked order ID, store and normalized code permits financial-fact preservation and legitimate refund/return under the canonical guards even when no concrete coupon can be identified. It never invents a reservation, acquires a guessed coupon, changes a count or permits new inventory capture/dispatch. Matching receipts on uncaptured eligible orders commit cancellation and FIN-003 compensation; already captured/shipped fulfillment is preserved, including paid duplicate replay. If cancellation is legally blocked, retain the receipt and an existing FIN-003 review claim. Unexplained missing rows/schema still fail closed. The issue fence rejects **all** post-migration inserts/updates/deletes, including marked writers, so knowing the v1 marker cannot forge this exception. Issue review/import is outside this task. This refinement preserves accepted legacy money facts without granting unsafe fulfillment.

## Migration, reconciliation and mixed binaries

Migration `202611170001_coupon_reservations.up.sql` is one transaction. Acquire explicit bounded/NOWAIT table locks in documented order for orders, checkout attempts, payment transactions, verification/receipt tables and coupon definitions before snapshot/backfill/fence installation; retry the entire migration if a live writer prevents a consistent drain. Use the existing migrator checksum/history protocol. No edits to older migrations.

For every persisted nonempty discount code, normalize store/code and resolve exactly one coupon in that store. Copy order amounts unchanged; never recalculate against current coupon pricing. Matched orders with confirmed payment or paid/refunded/captured history consume capacity conservatively; unresolved contradictory evidence is review-held. Active unpaid pending/processing orders reserve, including already-overdue orders until the actual expiry transition runs. Cancelled orders release only with the eligibility proof above; failed/unknown/no-deadline/inconsistent cases retain capacity and an issue. Null historical coupon-only amounts are honest attribution gaps and do not by themselves erase a matched reservation. Zero aggregate historical code claims retain a visible issue and conservative hold. Unmatched/ambiguous identity gets an issue and admission block rather than a fabricated coupon.

Rebuild count from these rows, including pending orders. Store old/new count and report `rebuilt > max_uses`; keep all existing accepted orders and amounts, even if oversubscribed. Future admission remains exhausted until genuine eligible release brings occupied below the limit. Migration is idempotent through canonical history and checksums; down refuses populated reservation/evidence tables.

Install narrow transaction-local `sellersho.fin007_writer='v1'` BEFORE fences, following FIN-005. Reject absent marker with SQLSTATE `55000` before taking any owner guard. Payment and fulfillment child fences do not acquire parent locks. The marked reservation-admission fence takes/reuses its exact coupon owner guard at rank350 before the subordinate insert and product guards; the canonical creator already preholds it. Protect coupon-backed order insertion/deletion and actual identity/amount/cancellation/payment-admission changes; related payment/inquiry/receipt inserts or relevant status changes; coupon count writes; reservation/evidence writes. Reject old standalone increment even when its predicate would otherwise succeed. New callers set the marker only in their guarded transaction. Deferred consistency proves evidence/state/count, so the marker alone is not authorization. Unrelated order metadata/refund bookkeeping must not fail merely because a row has a coupon. Immutable accepted identity/amount and terminal reservation rules apply even to marked writers.

The ledger fence is installed after backfill and rejects all runtime `legacy_snapshot` reservation inserts, including marked writers. Migration origin cannot be claimed by a runtime admission to bypass capacity, dates, revision or receipts. Supplier shipment insertion/update that creates a new physical dispatch is also fenced for coupon-backed parents; it requires the adopted writer and a concrete nonreleased reservation. The child fence reads parent identity without acquiring parent row locks. Existing shipped/delivered custody and subsequent carrier progress, failure holds and same-dispatch replay remain valid for immutable unresolved historical identities. A different pending leg on that order is new dispatch and stays denied. Drain `supplier_shipments` with the other source tables before installing these fences.

Runtime admission timestamps are assigned by the database fence after taking/reusing its coupon `FOR UPDATE` owner guard, regardless of supplied `created_at`. It then validates the window. This also protects a marked SQL writer that inserts its reservation before attempting the counter update and waits beyond expiry. Deferred window validation uses the same trusted instant, preserving a valid admission if commit follows expiry. Runtime release proof also covers genuine migration-origin reservations: unresolved inquiries, existing receipts and booked/unknown payment evidence retain capacity. The late-receipt exception applies to a reservation already released, including historical reservations, and cannot justify a new release. Locked already-shipped aggregate history may progress to delivered or replay; this does not authorize reverse or never-dispatched fulfillment.

`deploy_remote.py` currently migrates before replacing the running backend and may restore old code while retaining additive data. Therefore the database fence is mandatory: pre-migration writers finish before migration locks; queued/post-migration old writes fail closed, with nondiscounted/unrelated traffic preserved. An old-code rollback cannot restore coupon write availability and must explicitly report the retained fence. Never remove the fence or restore a database backup merely to make old writers work. Root verifies an actual frozen old server binary against the migrated disposable database, including old checkout, payment, cancellation and expiry paths; hand-written old SQL alone does not satisfy this gate.

## Acceptance

- 100 simultaneous distinct checkout attempts for maxUses=1: exactly one discounted logical order/reservation, count 1; 99 explicit exhaustion errors. Same-key concurrency/lost-response replay: one original order, original amount and reservation, even after deactivation/exhaustion.
- Real-schema two-connection barriers prove same-store creators hold compatible principal `KEY SHARE` locks without upgrades; creators on independent coupons progress independently; creator versus existing lifecycle follows the same principal order without FK inversion. Cover customer/store/referrer/supplier and origin-warehouse parents, duplicate order identity and discovered-parent drift.
- Rollback at order/line/origin/shipment/reservation/count/attempt seal restores all availability; commit-response loss does not. Unlimited, exact date boundaries, lock wait across end time, term/revision drift, zero benefit, campaign-only and multi-layer amount identity pass.
- Real two-connection barriers cover payment versus expiry/cancel, inquiry versus cancel, release then late verification, duplicate receipts and stock-admission failure after receipt; exactly one legal state path, original money facts and compensation preserved, no new use after release.
- Migration preserves paid/refunded/cancelled/pending/failed/overdue/no-deadline histories and their exact prices; reports oversubscription/unmatched/ambiguous/zero/uncertain cases and blocks unsafe admission. Metadata edits/deletion cannot detach evidence.
- Failure injection at receipt, coupon transition, event/count, cancellation/refund and commit consistency boundaries proves atomic rollback/recovery. Wrong store/code/amount/version, forged lifecycle transitions and missing marker fail closed. Count divergence is detected, never repaired by concealing orders.
- Actual old-binary fence rehearsal includes in-flight pre-migration and queued post-migration transactions, safe nondiscounted operations, new binary success and rollback behavior. Root full existing finance/inventory/checkout/worker suites and production health verification remain required.
